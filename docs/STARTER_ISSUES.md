# Preparing a starter issue

Use `good first issue` for a small, self-contained task a newcomer can verify. Use `help wanted`
when community help is welcome but the task needs more project knowledge. Choose the existing
`track:` label matching the work so the [skill picker](FIRST_PR.md#pick-a-task-2-minutes) finds it.

Before adding the starter label:

- Confirm the problem still exists on main and search for overlapping PRs.
- State the problem, the file or area to start in, and what is outside scope.
- Give a reproducible example or a source for a factual correction.
- Give the exact check and expected result; name required tools.
- Link the recipe and explain access, rendering or credential requirements.
- Check that the task does not depend on a pending maintainer decision.

Use `blocked` for unresolved dependencies and `reserved:maintainers` for work set aside for
maintainers. Assign active work or link its PR with a closing reference. Read comments before
starting a batch so work volunteered there is not duplicated. Remove the starter label when a
task no longer meets the criteria.

Keep the original conversation and update an issue when its facts change. Do not close/reopen
issues or toggle labels to manufacture activity. An empty filtered track is useful information;
do not fill it with unsuitable tasks.

Sources: [GitHub label guidance](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/encouraging-helpful-contributions-to-your-project-with-labels)
and [contributor guidance](https://docs.github.com/en/get-started/exploring-projects-on-github/finding-ways-to-contribute-to-open-source-on-github).
